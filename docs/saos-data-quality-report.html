SAOS Data Quality

Problems identified in results/saos-data-quality.csv and their treatment

Dataset context. The report covers the SAOS common-court dump and the derived modelling datasets. The CSV contains 32 checks. Counts refer to the denominator shown in the table; they are not all counts of modelling rows.

Executive summary. The main modelling limitation is not isolated text noise, but selective coverage and uncertain pairing. Most appeals do not have a recoverable first-instance judgment in SAOS. Rows with an empty required text, an unconfirmed pair, or an unrecognised outcome are excluded from the final modelling dataset. Source records remain available in intermediate tables for audit and diagnostics.

Model relevance

CriticalPotentially assigns the wrong first-instance text to the appeal outcome. Such pairs are excluded from modelling.
HighCan lose rows, create wrong pairs or labels, or bias the selected modelling sample.
MediumCan weaken metadata or text features and affect selected subsets, but does not necessarily invalidate the row.
LowMainly affects auditability, temporal interpretation, or optional metadata not used by the current text input.

Detailed issue 1: SENTENCE record with empty textContent

A SAOS record of type SENTENCE may contain metadata such as an identifier, court, case signature and date, while its textContent is empty. The report finds 21,256 of 357,527 sentence records (5.95%). The example record is 491584.

Why this is not automatically a parser error

The public SAOS API can return the record with an empty text field and no usable alternative in fields such as decision or judgmentResult. The missing text therefore cannot safely be reconstructed by our parser.

Concrete example — SAOS record 491584. The API returns judgmentType = SENTENCE, caseNumber = II K 11/03, judgmentDate = 2003-05-06, and two judges, but textContent = "". It also returns decision = null and judgmentResult = null. The record therefore proves that the judgment metadata exists, but provides no sentence text that the model can read.

Separate SENTENCE and REASONS records

SAOS can store separate records for the same court and signature:

  • SENTENCE contains the operative part;
  • REASONS contains the written reasons.

The pipeline groups them by case_key. It can use reasons from a separate REASONS record, or from a SENTENCE record that also contains reasons. However, available reasons do not recreate a missing operative part.

Pipeline treatment and model impact

The case-building step keeps the sentence and reasons identifiers separately. The final dataset requires both first_operative_len > 0 and first_reasons_len > 0. Therefore a case with an empty first-instance sentence is retained in intermediate data but excluded from the final model dataset.

Decision: excluded from modelling data. Do not invent or infer a missing sentence from metadata or reasons. Keep the record for audit, but do not use it as a complete text input.

The broader risk is selection bias: missing text may vary by court, period, or publication practice. The final model is therefore trained on the subset with usable published text, not on all SAOS cases.

Detailed issue 2: REASONS record with empty textContent

A SAOS record of type REASONS may exist because reasons were announced or registered, while its textContent is empty. The report finds 4,823 of 53,072 reasons records (9.09%). This is different from an empty sentence: the operative part may still be available, but the written reasoning needed by the model is missing.

Important denominator clarification. The value 4,823 is a count of raw SAOS REASONS records with empty textContent. It is measured before combining separate SENTENCE and REASONS records belonging to the same case_key. It is therefore not a count of 4,823 final modelling cases excluded after the pipeline has checked whether another record provides usable reasons.

How the records can complement each other

The pipeline groups records with the same court and case signature. It first looks for a non-empty separate REASONS record. If that is not available, it can use reasons embedded in a non-empty SENTENCE record. An empty REASONS record therefore does not automatically mean that the whole case has no reasons, but it does mean that this particular record contributes no reasoning text.

Concrete example — SAOS records 418676, 391901 and 424568. The API returns respectively judgmentType = REASONS for case signatures XVII AmC 334/09, II Ka 124/12 and VII K 266/12, but each has textContent = "". Their metadata and dates are present, yet there is no written reasoning in those records for the model to read.

Pipeline treatment and model impact

When the same case has a non-empty sentence containing reasons, or another non-empty reasons record, the available text can still be used. When no reasons text is available, the final dataset condition first_reasons_len > 0 excludes the case. The empty record itself is retained in intermediate data for audit and coverage analysis.

Decision: excluded from modelling data when no usable reasons text exists for the case. Do not treat an empty reasons record as an empty string that the model can meaningfully learn from, and do not infer reasons from metadata. Use the case only when usable reasons text is available from another record.

Detailed issue 3: matched by signature but header date disagrees

The pairing pipeline connects an appellate judgment to the first-instance judgment it reviews. It uses the signature, court hierarchy, court name from the appellate header, and the first-instance judgment date.

What the 1,215 cases mean

The CSV reports 1,215 of 13,585 matched candidates (8.94%) where the candidate date differs from the date in the appellate header. The old wording said “date or court disagrees”, but that was imprecise: a candidate whose court name disagrees is rejected before it becomes a matched candidate. Thus this row primarily measures date disagreement.

Why a matching signature is not enough

A signature such as I C 312/12 is not globally unique. Similar signatures can occur in different courts, and one court can have multiple records for a signature because of a retrial, partial judgment, duplicate upload, or another publication event. A wrong pair would look like:

text of first-instance judgment A → outcome label from appeal concerning judgment B

Why we take the conservative approach

The date discrepancy may be a source typo, a difference between announcement and preparation dates, a parser problem, or a different judgment with the same signature. Without independent evidence, automatically accepting the pair could introduce a wrong text-target association.

Concrete example — case key 275|VI ACa 630/11. This is one of the CSV examples in the 1,215-row group. The pairing process found a first-instance candidate by signature and court hierarchy, but the candidate's judgment date did not equal the date written in the appellate header. The pair is therefore kept for diagnostics in pairs.parquet, but excluded from the modelling dataset rather than assigning a potentially wrong first-instance text to the appeal label.
Decision: pairs with a header-date disagreement are excluded from the final modelling dataset but retained in pairs.parquet for diagnostics. Court-mismatched candidates are also not accepted.

Detailed issue 4: judgment date outside 1990–2026 or unparseable

The report identifies 3 of 474,894 common-court records whose source judgment date is outside the expected 1990–2026 range or cannot be parsed as a valid date. These are source-data anomalies, not ordinary differences between the date of a judgment and the date on which it was published.

Concrete examples and exact evidence.
  • 358516, case II K 336/17, has source date 0208-03-14. It is corrected to 2018-03-14 because the same-court, same-signature SENTENCE record 358515 has judgment date 2018-03-14.
  • 227221, case II K 84/16, has source date 2101-04-14. It is corrected to 2016-04-14 because the text header says “Dnia 14 kwietnia 21016 r.”, the text gives hearing dates 10.03.2016 and 14.04.2016, and the SAOS source identifier refers to the 2016 upload.
  • 31345, case I ACa 772/13, has source date 3013-12-04. It is corrected to 2013-12-04 because the judgment text says it was heard on “4 grudnia 2013 r.” and the SAOS source identifier includes 2013-12-04.
These are record-specific evidence chains, not assumptions based only on the date range.

Treatment

Each correction is an explicit record-ID rule in the preprocessing step, documented in data/CLEANING.md. The rule first verifies that the source still contains the expected erroneous value and raises an error if it has changed. This prevents a correction from silently being applied to a different record. No general rule guesses a year for every malformed date.

Decision: correct the three verified source typos in preprocessing and retain the corrected dates in derived data; preserve the original anomalies in the quality report for audit.

Detailed issue 5: published before the judgment date

The report finds 44 of 474,894 records (0.01%) where the SAOS source.publicationDate is earlier than the record's judgmentDate. This is a metadata consistency warning, not proof that a published document existed before the court actually issued the judgment.

Concrete examples.
  • Record 199625 has judgmentDate = 2016-02-13 and publicationDate = 2016-02-10. Its text header says “dnia 13 stycznia 2016 roku”, so the text itself indicates a date earlier than the API judgment date. This points to an inconsistent judgment-date field, not necessarily an impossible publication.
  • Record 175911 has judgmentDate = 2016-05-26 and publicationDate = 2015-09-09. The record must be treated as a source metadata anomaly until the original court publication history is independently verified.

Treatment

We do not apply a general date correction based only on this comparison. The text date, source identifier, and publication history can have different meanings, and the CSV check alone cannot establish which field is wrong. The records remain available for modelling when they pass the ordinary text and pairing filters. The anomaly is retained for audit, while publication_date is not used as the modelling or temporal-split date.

Decision: retain in modelling data; flag for audit and do not use publication_date as the modelling date.

Detailed issue 6: reasons record dated before its sentence

The report finds 152 of 39,654 cases with separate SENTENCE and REASONS records where the REASONS record has an earlier judgmentDate than the sentence record. The comparison is a metadata consistency check; it does not compare the dates printed inside the documents.

Concrete examples. The CSV lists 276|XVII AmC 334/09, 276|XVII AmC 935/09, and 276|XVII AmC 124/07. For each, the derived case table contains separate sentence and reasons records, and the reasons-record date is earlier than the sentence-record date. The current checkout does not contain data/interim/records.parquet, so the exact two source dates for these examples cannot be independently reproduced here.

Interpretation

This may be a source-date problem, a record-linking problem, or a difference in date semantics. A reasons record can be dated when the reasons were written, registered, or imported, while the sentence record can carry the date of the hearing or judgment. The anomaly is therefore not sufficient by itself to declare the text unusable.

Treatment

We do not reorder or discard a case solely because the reasons-record date precedes the sentence date. If the case has usable sentence and reasons text and passes the ordinary pairing checks, it remains eligible for modelling. The date anomaly is retained for audit and is not used as a model feature or as the temporal split date.

Decision: retain if the case has usable text and a valid pairing; flag the date anomaly for audit.

Detailed issue 7: reasons record dated more than one year after its sentence

The report finds 121 of 39,654 cases (0.31%) with separate SENTENCE and REASONS records where the reasons-record date is more than 365 days later than the sentence-record date. This is a record-date gap, not evidence that the written reasons are necessarily wrong or unusable.

Concrete examples. The CSV lists 39|II K 11/03, 159|III Ca 1544/16, and 276|XVII AmC 5200/11. These cases have separate sentence and reasons records, with the reasons record dated more than a year after the sentence record. The current checkout does not contain data/interim/records.parquet, so the exact source dates for these examples cannot be independently reproduced here.

Interpretation

A written justification may be prepared, registered, uploaded, or published long after the judgment was announced. The two records may therefore use different date semantics. A large gap can also indicate a source metadata error or an incorrect record association, so it should remain visible in the quality audit.

Treatment

We do not exclude a case solely because the reasons date is more than one year later. If the selected sentence and reasons texts are usable and the appeal pairing is valid, the case remains eligible for modelling. The date is not used as a model feature or as the temporal split date.

Decision: retain if the case has usable text and a valid pairing; flag the date anomaly for audit.

Detailed issue 8: case signature not in the standard form

The report finds 1,810 of 474,894 records (0.38%) whose case signature is not parsed into the standard roman-division, code, number, and year structure. The parser represents this by leaving code empty. This is a parser-recognition problem, not proof that every source signature is invalid.

Concrete example. The most common examples are IV 1 P 51/11, IV 2 P 365/10, and XI 1Ca 508/13. In particular, IV 1 P 51/11 has an extra digit after the division numeral. The current regular expression expects the roman division to be followed directly by the letter code, so it does not recognise this local subdivision format.

Why this matters

A signature is used to classify the legal domain, determine whether a case is first-instance or appellate, build the case_key, and find matching first-instance judgments. If parsing fails, the record can be lost from domain-specific processing or cannot be paired reliably. On the other hand, the 1,807 digit-after-division examples may be valid court-specific notation, so rejecting them solely because they differ from the common format would lose potentially usable data.

Treatment

We do not apply a blanket correction or silently rewrite these source signatures. A record is eligible only if its signature can be parsed unambiguously and the resulting case passes the normal court, date, text, and pairing checks. Records that remain unparsable or cannot be paired are excluded from modelling data, while the original signature is retained for audit.

Decision: local signature variants are not rejected solely for their format; successful parsing and pairing are required before modelling.

Other handling rules

  • Verified source date typos are corrected by explicit record-ID rules and documented in data/CLEANING.md.
  • Empty appellate sentences, missing headers, missing first-instance signatures, and unrecognised outcomes are not used to form reliable modelling rows.
  • An empty extracted ruling after the header is an implementation issue: the extraction must be fixed or checked against raw text before excluding a source record as truncated.
  • SAOS judgmentIds are identifiers of cited judgments. They are not treated as an error or as the primary appeal-pairing mechanism.
  • Short first-instance text is flagged, not automatically called truncated: it can be a valid short decision or an incomplete text.
  • Missing presiding-judge role metadata is reported separately for the final modelling set: 398 of 10,644 rows (3.74%). Of these, 54 have exactly one judge and can be corrected deterministically; 340 have no judge and 4 remain ambiguous.

The complete issue table, including counts, examples, importance and treatment for all checks, is maintained separately in results/saos-data-quality.csv.
